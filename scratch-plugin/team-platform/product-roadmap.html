先理解一个决定全局的限制

Web 页面在哪台电脑打开，不代表 Agent 就在哪台电脑执行。

!
员工只通过浏览器访问服务器 A 时，DSH Host 的文件、Bash 和 Git 默认都在服务器 A 执行。

浏览器受安全沙箱限制，服务器 A 不能直接读取员工电脑上的 C:\project、本地 Git 状态和未 Push 的 Commit。要操作员工本地代码，必须增加本地执行端；否则代码仓库必须放在服务器 A。

三种可行部署方式

路线图推荐先走“服务器独立工作区”，因为它最符合当前服务器 A 的架构，也最容易验证。

第一版推荐

A. 服务器独立工作区

每个用户在服务器 A 拥有自己的仓库副本或 Git Worktree，DSH 在对应目录执行。

  • 服务器能直接读取 Git
  • 容易采集 Diff、Commit 和测试
  • 必须做好目录、进程和工具权限隔离
  • 适合先做公司内部 MVP
后续能力

B. 员工电脑本地执行端

员工安装轻量客户端，本地客户端执行文件、Bash 和 Git，服务器负责任务与数据管理。

  • 可以使用员工现有代码目录
  • 体验最接近日常本地开发
  • 需要安全通信、设备认证和升级机制
  • 实现难度明显更高
只做补充

C. 仅连接 Gitee API

服务器只读取已经 Push 的 Commit、PR、Issue 和 CI。

  • 无需访问员工本地电脑
  • 适合确认最终远程成果
  • 看不到未提交和未 Push 的工作
  • 不能让服务器 Agent 操作本地代码

建议的 6 个实施阶段

点击阶段可展开。每一阶段都明确“做什么、保存什么、能达到什么效果”。

0

确定代码执行架构

先决定员工操作的是服务器仓库，还是本地仓库。

要做什么

  • 第一版选择服务器独立工作区
  • 每个用户分配独立目录
  • 确定仓库克隆、更新和删除规则

安全要求

  • 用户不能切换到他人目录
  • Bash/文件工具限制在自己的工作区
  • 进程和凭据按用户隔离

验收

  • 两个用户同时工作互不影响
  • 不能读取另一用户仓库
  • Session 的 cwd 属于当前用户
达到效果：平台第一次具备可信的多用户研发运行基础。没有这一步，Git 数据和用户隔离都不可靠。
1

Session 自动识别 Git 上下文

创建会话后识别仓库、Remote、分支和 HEAD。

读取

  • git rev-parse --show-toplevel
  • git remote get-url origin
  • git branch --show-current
  • git rev-parse HEAD

保存

  • session_id / user_id
  • 仓库根目录与 Remote
  • 分支、HEAD、采集时间
  • 是否为非 Git 目录

原则

  • 只读 Git 命令
  • 异步采集，失败不阻断会话
  • 不保存代码正文
达到效果：后台能回答“谁在哪个仓库、哪个分支使用了哪个 Session”。
2

后台增加“代码活动”页面

把 Git 上下文变成开发者和管理员看得懂的页面。

页面信息

  • 成员、会话、仓库
  • 分支、HEAD、更新时间
  • 是否存在工作区修改

查询能力

  • 按成员筛选
  • 按仓库与分支分组
  • 手动刷新 Git 状态

验收

  • 页面结果与命令行一致
  • 非 Git Session 有清晰状态
  • 普通用户只看自己的数据
达到效果：当前的“使用量后台”升级为“项目与代码环境可见后台”。
3

保存关键 Git 快照

不记录每句对话，只在关键时间点保存文件变化摘要。

采集时机

  • Session 创建：初始快照
  • 回合结束：轻量刷新
  • HEAD 变化：成果快照
  • 后台手动刷新：最新快照

保存摘要

  • M/A/D/R 文件列表
  • 新增与删除行数
  • 暂存与未暂存状态
  • HEAD 和采集时间

不保存

  • 源代码全文
  • 完整 Diff
  • 每轮重复快照
  • 员工本地无关目录
达到效果：能展示“Session 开始前已有修改”和“使用期间检测到的新增变化”，但不宣称全部由 Agent 产生。
4

关联 Commit 与测试结果

用确定性成果证明工作发生，而不是只看聊天和 Token。

Commit

  • 检测 HEAD 变化
  • 读取 SHA、作者、Message
  • 读取文件与行数摘要
  • Commit 无需由 Agent 执行

测试

  • 项目配置验证命令
  • 保存退出码与执行时间
  • 关联运行时 HEAD
  • 后续接 CI 报告

边界

  • 记录“期间检测到 Commit”
  • 不声称 Commit 全由 Agent 编写
  • 外部 Git 客户端提交也能检测
达到效果：平台开始回答“AI 使用期间是否形成代码提交、是否经过测试”。
5

自动归集为工作活动

员工不选任务，平台按确定性规则自动汇总多个 Session。

归集规则

  • 同一用户
  • 同一 Remote 和分支
  • 时间连续
  • HEAD 与文件变化相关

形成记录

  • 起止时间
  • 相关 Session
  • 文件变化与 Commit
  • 测试结果

员工操作

  • 默认自动归集
  • 必要时确认或拆分
  • 不强制先建任务
达到效果：后台以“一段连续研发工作”展示数据，而不是堆积零散 Session。
6

LLM 总结与经验审核

最后才让 LLM 理解过程，原始采集不依赖 LLM。

输入

  • Session 关键事件
  • Git 文件变化摘要
  • Commit Message
  • 测试结果

生成

  • 完成了什么
  • 涉及哪些模块
  • 遇到哪些失败
  • 如何验证

治理

  • 始终标记“AI 草稿”
  • 员工确认后生效
  • 有复用价值才转经验/Skill
达到效果：经过成果和验证支撑后，平台才能形成可信、可搜索、可复用的公司经验。

现在先做什么

按你的部署方式，不能直接跳到“读取员工本地 Git”。第一步应先验证服务器工作区方案。

  1. 在服务器 A 为测试用户建立两个独立仓库目录或 Worktree。
  2. 确认 DSH Session 的 cwd 指向当前用户自己的服务器目录。
  3. 服务端验证用户无法访问另一人的目录、Shell 和 Git 状态。
  4. 隔离验证通过后，再实现 Session 创建后的 Git 上下文采集。
  5. 最后增加后台“代码活动”页面。
