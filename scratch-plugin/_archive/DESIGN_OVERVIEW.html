Session 同步设计

多台本地 DSH 的会话过程记录 → 服务器归档 · 文件为真相 · 增量 + 验证 + 可重建

两层模型：文件为真相，数据库为派生索引

会话文件（多帧 zstd 压缩 JSONL）是官方持久化格式，可重放、格式版本化——它是权威。PG 只是派生索引：归属（真元数据）+ 同步标记（可从文件重算）。文件系统与数据库无法原子，因此采用「写路径尽力同步 + 对账兜底」——对象存储 / 事件溯源同款模式。

┌─ 本地 DSH（真相）─────────────┐   ┌─ 服务器（副本 + 索引）───────────────┐
│ session.jsonl.zstd          │   │ <root>/session.jsonl.zstd（DSH 原生） │
│  （追加式事件日志）           │ ◄─┼ 字节增量 →                         │
│                             │   │ PG team_session_log:               │
│                             │   │   session_id / user_id（归属）      │
│                             │   │   content_md5 + file_size（标记）   │
└─────────────────────────────┘   └────────────────────────────────────┘

同步时机（四个触发点）

触发时机理由
主session/flushDSH 持久化提交边界（turn/step 结束）事件只在提交点落盘；频率=工作节奏，非每 chunk
session/created新会话创建立即注册归属
session/disposed会话销毁收尾不遗留
挂载/登录补传重启 / 登录对账历史会话（含冷会话）

不用定时器（数据只在提交边界变）；不用事件级触发（每 chunk 太频繁）。

单次同步流程

① 拉取标记GET status → { fileSize, contentMd5 }
→
② 本地算 md5stat + 读文件指纹
→
③ 决策一致 / 前缀一致 / 无标记
→
④ 上传跳过 / 增量 / 全量替换
→
⑤ 更新标记content_md5 + file_size
③
完全一致（size + md5 都匹配）→ 跳过（零传输）
③
前缀一致（md5(本地[0..fileSize]) == 标记）→ 增量：只传 [fileSize..末尾] + baseSize + baseMd5
③
无标记 / 不一致 → 全量替换（tmp + rename 原子写）→ 落盘后 inspect 首帧校验，失败则删文件 + 清标记

每次同步前拉 server 标记（而非本地记）：本地内存崩溃即丢、压缩会重写文件；server 标记是唯一权威。

安全性：为什么不会损坏

md5 前缀校验

增量前证明本地前缀与 server 已存一致；不一致（压缩重写）改全量，绝不追加到错误基底。

server 双重校验

增量携带 baseSize+baseMd5，与自身标记比对；不符 → 409 要求全量。

原子替换

全量写临时文件 + rename，读方永远看不到半帧。

大小校验

追加后 stat 文件 == totalSize，不符 → 409 重建。

版本门控

header.version ≠ SESSION_FORMAT_VERSION → 415 fail-closed，格式演进保护。

首帧校验

全量落盘后 inspect：首帧必须恰好一行 session header；否则删文件 + 清标记 + 拒绝——无头文件永不入库，启动/列表不再被拖崩。

读稳定性

client 读文件后复检大小：DSH 正在写（半写/截断）则跳过本轮，损坏内容从源头不出门。

核心任何异常 → 409 → 全量重传（幂等自愈）——正确性永远由全量替换兜底，不存在死路。

容错自愈

场景行为
断网失败 → 下次触发重试（替换幂等）
重启补传拉标记 → 已同步跳过 / 部分增量 / 缺失全量
压缩重写本地文件前缀 md5 不一致 → 全量
并发触发每会话单飞锁（syncing）；server 409 兜底
server 换根 / 文件被清补传标记不符 → 对账修复
单个文件损坏（无头/半写）上传被首帧校验拒绝 + 清标记 → client 下次全量重建；client 读稳定复检防半写
增量基准在、文件却没了增量前 server 确认目标文件存在，缺失 → 409 全量（防增量重建出无头文件）

对账（Reconcile）：文件变了，数据库跟着变

1
PG 有行、文件不存在 → 删除该行（存在性以文件为准）
2
文件存在、PG 无行 → 孤儿（记录，不删文件——无法自动定归属）
3
标记与文件不符 → 以文件重建（重算 md5 + size）

触发：server 启动自动 + 管理后台手动按钮。索引允许漂移但例行收敛——不是事务强一致，而是最终一致 + 对账。

演进史：从复杂到简单（设计取舍）

v1 增量事件 + seq 游标 + 连续性校验复杂度爆炸：游标跨根失效、压缩 seq 空洞、无限重试、崩溃窗口重复——每个机制都引入一类 bug
↓
v2 整文件上传（替换）简单正确，但 O(n²) 带宽：会话越长每次上传越大，100 人并发撑不住
↓
v3 md5 校验的字节增量（最终）日常 O(增量) 传输，任何异常回退全量；md5 指纹取代所有游标/连续性状态机；全量后首帧校验 + client 读稳定复检兜底

认知分布式同步的正确性 = 验证 + 幂等 + 可重建，不是状态永远一致。

多用户隔离设计

Server 统一认证 · 凭证 Host 托管 · 数据按用户三层隔离 · 员工机器碰不到真密钥

架构全景：两类消费者 × 两套认证 × 三层隔离

① 认证层
   机器（本地 DSH Host）  → Bearer token   （Redis team:client-token · Host 托管）
   浏览器（管理员）       → HttpOnly Cookie（Redis team:session · 浏览器自动携带）

② 数据层
   team_session_log：session_id → user_id（跨用户冲突被 DB 约束拒绝）
   文件为真相（session.jsonl.zstd 副本）+ PG 派生索引 + 对账兜底

③ 接口层
   端点 Bearer → userId → 只允许操作自己的会话（403/404 区分）· 查询按 userId 过滤

认证细节

机制载体Redis key生命周期消费者

code 只能换一个新会话、不能调任何 API；即使出现在浏览器历史，过期即废。

隔离的三层落实

层次机制
存储层归属绑定约束：INSERT ... ON CONFLICT DO UPDATE ... WHERE user_id = EXCLUDED.user_id → 跨用户改写不可能
查询层listOwnSessions(userId) 按 userId 过滤；管理端才可见全量
接口层每个 /team/api/* 先 Bearer → userId → 再查归属 → 403（非本人）/ 404（不存在）

五个技术亮点

Token 永不进浏览器

凭证只存在于 Host 进程（credentials 文件 + 内存），不进 devtools / 历史 / localStorage，泄露面最小化。

两套认证 = 两类消费者

机器要可携带的 Bearer，浏览器要自动携带的 Cookie；合并会暴露 token 或需嗅探调用方。

SSO 短命 code 桥接

泄露窗口从 7 天（token）缩到 30 秒（code），用途单一、消费即删——OAuth2 authorization code 同款。

模型网关凭证代换

公司 token → server 内部换真 DEEPSEEK_API_KEY → 流式转发，真 key 不出 server。

隔离靠 DB 约束而非信任

跨用户操作在存储层被拒绝，不是客户端自觉。

面试追问要点

问题回答
为什么不共享 Cookie？生产环境 client=127.0.0.1、server=公司域名，Cookie 跨域不共享，SameSite/Secure 全踩坑
为什么不用 JWT？Redis 会话可服务端撤销、可滑动续期、O(1) 校验；JWT 无状态但撤销要黑名单
隔离在哪几层？存储（约束）→ 查询（过滤）→ 接口（鉴权）三层
为什么不用加盐 md5？内容指纹非秘密，盐是密码哈希概念；加盐会破坏对账重算比对
已知取舍？明文密码、token 未哈希、禁用不即时生效——识别了风险，按 MVP 优先级后置
