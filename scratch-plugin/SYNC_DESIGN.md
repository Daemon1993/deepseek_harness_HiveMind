# DSH Session 同步设计（面试版）

> 多台本地 DSH → 一台服务器 DSH 的会话同步。文件是真相，数据库是派生索引；
> 正确性靠"验证 + 幂等 + 可重建"，不靠状态永远一致。

## 1. 问题

- 员工本地 DSH 产生会话（过程记录：prompt、工具调用、模型输出）
- 需要同步到服务器 DSH 供管理员分析
- 单向（本地 → 服务器）；断网/重启/并发下不丢不坏；100+ 用户规模可控

## 2. 架构：文件为真相，数据库为索引

```
本地 DSH（真相）                    服务器（副本 + 索引）
──────────────────                ──────────────────────
session.jsonl.zstd  ←──字节增量──→  <root>/session.jsonl.zstd（DSH 原生格式）
  （追加式多帧 zstd JSONL）          （字节相同的副本）
                                   PG team_session_log：
                                     session_id / user_id（归属，真元数据）
                                     content_md5 + file_size（同步标记，派生）
```

- **文件是权威**：DSH 官方持久化格式，可重放、格式版本化（SESSION_FORMAT_VERSION 门控）
- **PG 是派生索引**：归属（真元数据）+ 标记（可从文件重算）
- 文件系统 + 数据库无法原子 → **写路径尽力同步 + 对账兜底**（对象存储 / 事件溯源同款模式）

## 3. 同步时机（四个触发点）

| 触发 | 时机 | 理由 |
|---|---|---|
| `session/flush`（主） | DSH 持久化提交边界（turn/step 结束） | 事件只在提交点落盘；频率=工作节奏 |
| `session/created` | 新会话 | 立即注册 |
| `session/disposed` | 销毁 | 收尾 |
| 挂载/登录补传 | 重启/登录 | 对账历史会话 |

不用定时器（数据只在提交边界变）；不用事件级（每 chunk 太频繁）。

## 4. 单次同步流程

```
① GET /team/api/sync/session/status?sessionId=X → { fileSize, contentMd5 }
② 本地 stat + 读文件算 md5
③ 决策：
   完全一致（size+md5）      → 跳过（零传输）
   前缀一致（前缀 md5 匹配） → 增量：传 [fileSize..末尾] + baseSize + baseMd5
   无标记 / 不一致           → 全量替换
④ 上传：
   增量 → server 校验 baseSize+baseMd5 → 追加 → 校验 size == totalSize
   全量 → 原子替换（tmp + rename）
⑤ server 更新标记
```

每次同步前拉 server 标记（而非本地记）：本地内存崩溃即丢、压缩会重写文件；server 标记是唯一权威。

## 5. 安全性

1. md5 前缀校验：增量前证明本地前缀与 server 已存一致
2. server 双重校验：baseSize+baseMd5 vs 自身标记，不符 → 409
3. 原子替换：tmp + rename，读写不见半帧
4. 大小校验：追加后 stat == totalSize
5. 版本门控：header.version 不符 → 415 fail-closed

**任何异常 → 409 → 全量重传（幂等自愈）**，正确性永远由全量替换兜底。

## 6. 容错自愈

| 场景 | 行为 |
|---|---|
| 断网 | 失败 → 下次触发重试 |
| 重启 | 补传拉标记 → 跳过/增量/全量 |
| 压缩重写 | 前缀 md5 不一致 → 全量 |
| 并发触发 | 每会话单飞锁；server 409 兜底 |
| server 换根/文件被清 | 补传标记不符 → 对账修复 |
| 单文件损坏 | 对账删除 + client 重建；分析端点容错降级 |

## 7. 对账（Reconcile）

- 文件是权威，索引允许漂移但例行收敛
- 规则：PG 有行文件无 → 删；文件有 PG 无 → 孤儿（不删文件）；标记不符 → 以文件重建
- 触发：server 启动自动 + 管理后台手动按钮

## 8. 演进史（设计取舍）

1. **v1 增量事件 + seq 游标 + 连续性校验** → 复杂度爆炸（游标失效、seq 空洞、无限重试、崩溃窗口）
2. **v2 整文件上传** → 简单正确但 O(n²) 带宽
3. **v3（最终）md5 校验的字节增量** → 日常 O(增量)，异常回退全量；md5 指纹取代所有状态机

核心认知：**分布式同步的正确性 = 验证 + 幂等 + 可重建**，不是状态永远一致。

## 9. 追问要点

- 为什么文件不是 DB blob：官方格式 + 复用读取代码，DB 只做查询面
- 为什么 md5 不用 size+mtime：内容级精确（压缩重写同大小同 mtime 也能识别）
- 为什么不做双向：业务只需归档/分析，单向大幅简化冲突
- md5 是内容指纹不是秘密：无盐；要防伪造可换 sha256（一行）
